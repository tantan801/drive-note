# 第 43 章 Linux 设备树

新版本 Linux ARM 平台驱动大量使用设备树 DTS。

---

## 43.1 什么是设备树

**设备树（Device Tree）**：采用树形结构来描述板级硬件信息。

**DTS（Device Tree Source）**：设备树源文件，描述开发板硬件：CPU 数量、内存基地址、I²C/SPI 总线上挂载哪些外设等。

**树形结构**：系统总线作为主干；IIC、SPI、GPIO 控制器是分支；IIC 控制器下面再接 IIC 从设备（FT5206、AT24C02、MPU6050）。

### 设备树出现的历史背景（没有设备树时代）

在 Linux 3.x 之前 ARM 架构没有设备树。板级硬件信息全部写在内核源码 `arch/arm/mach-xxx`、`arch/arm/plat-xxx` 下面的 C 源文件中。

- 每一款 ARM 板子，都要在内核新增一套板级 C 代码
- SOC 相同、板子外设不同，就要新增大量重复代码
- 大量冗余板级 C 文件硬编译进 zImage，造成内核代码"虚胖"

Linus 对 ARM 社区大量冗余板级代码很不满，因此 ARM 社区借鉴 PowerPC 架构，引入设备树。

### DTS 和 DTSI 分工

1. **`.dts`**：板级设备树，描述某一块开发板独有的硬件
2. **`.dtsi`**：设备树头文件，描述 SOC 芯片公共硬件资源（CPU、各个外设控制器）；多个 dts 可以 `#include` 引用同一个 dtsi，类似 C 语言头文件

> **核心思想**：把板级硬件信息从内核 C 源码剥离出来，放到独立的 dts/dtsi 文本文件。更换硬件板子，修改、编译设备树得到 dtb，不需要重新编译 zImage 内核镜像。

### 相关文件后缀概念

| 后缀 | 含义 |
|------|------|
| `.dts` | Device Tree Source，设备树源文件，描述某一块开发板板级硬件（I.MX6U-ALPHA 开发板对应的 dts） |
| `.dtsi` | Device Tree Source Include，设备树头文件，公共通用硬件描述，多个 dts 可以 include 引用，比如芯片 SOC 内部外设 |
| `.dtb` | Device Tree Blob，设备树二进制。DTS/DTSI 经过设备树编译器 dtc 编译得到 dtb 二进制；U-Boot 将 dtb 加载到 DDR 指定地址，传递给 Linux 内核 |
| `.dtc` | Device Tree Compiler，设备树编译器，把 `.dts` 编译生成 `.dtb` |

**工作流程：**
dts + dtsi —(dtc 编译)—> dtb —> uboot 加载 dtb 到内存 —> 内核解析 dtb，获取板级硬件信息

## 43.2 DTS、DTB 和 DTC

| 名称 | 说明 |
|------|------|
| DTS | 设备树源文件，文本，后缀 `.dts`，人工编写修改 |
| DTC | 设备树编译器（Device Tree Compiler），源码位于内核 `scripts/dtc` |
| DTB | 设备树二进制 blob，后缀 `.dtb`；由 DTC 编译 dts/dtsi 生成；U-Boot 加载到内存，传递给 Linux 内核解析 |

### 编译设备树命令

在内核源码根目录执行：

```bash
make dtbs       # 只编译设备树（推荐）
# make all     # 编译全部：zImage + ko 模块 + dtb
```

### 哪些 dts 会被编译？

文件路径：`arch/arm/boot/dts/Makefile`

```makefile
dtb-$(CONFIG_SOC_IMX6ULL) += \
    imx6ull-alientek-emmc.dtb \
    imx6ull-alientek-nand.dtb \
    ……
```

- 内核配置开启 `CONFIG_SOC_IMX6ULL=y`，列表里所有 `dtb-xxx` 对应的 dts 都会被编译
- 自己新做一块板子：新建 `xxx.dts`，在 Makefile 的 `dtb-$(CONFIG_SOC_IMX6ULL)` 下面添加对应的 dtb 文件名

### dtb 的使用（回顾移植知识点）

1. `make dtbs` 编译，输出 dtb 二进制
2. U-Boot 通过 tftp 将 dtb 下载到 DDR 指定地址
3. `bootz zImage - dtb地址` 启动内核
4. U-Boot 的 r2 寄存器传递 dtb 在 DDR 中的物理地址，内核启动之后解析 dtb，获取板级硬件信息

## 43.3 DTS 语法

实际开发几乎不会从零写 dts，一般是在 SOC 厂商提供的 dts/dtsi 基础上修改。设备树参考文档：`Devicetree Specification V0.2.pdf`、`Power_ePAPR_APPROVED_v1.12.pdf`

### 43.3.1 `.dtsi` 头文件

设备树支持 `#include` 头文件，可引入：`.h`、`.dtsi`、`.dts`。

- **`.dtsi`**：设备树头文件，存放 SOC 片上公共外设描述（CPU、UART、I²C、SPI 等）；多个板子 dts 可以 `#include` 同一个 dtsi
- **`.dts`**：板级设备树，描述某一块开发板独有的硬件

示例 `imx6ull-alientek-emmc.dts`：

```c
#include <dt-bindings/gpio/gpio.h>
#include "imx6ull.dtsi"
```

`imx6ull.dtsi` 里面完整描述 I.MX6ULL 片上全部外设：cpu、中断控制器、各个 uart、i²c、spi 等。

> 多个 dts/dtsi 中都写 `/ { ... };` 根节点，编译 dtb 的时候会自动合并为一个根节点，不会冲突。

### 43.3.2 设备节点

设备树整体树形结构，每一个硬件对应一个设备节点；节点由若干属性（键-值对）组成。

**节点命名格式：**

```c
label: node-name@unit-address {
    属性;
};
```

1. **label 标签**：别名，使用 `&label` 即可引用该节点，不用写完整长路径
2. **node-name**：节点名字，体现设备功能
3. **@unit-address**：外设寄存器物理基地址；有寄存器资源的节点必须带 `@+地址`；无寄存器可以省略

```c
intc: interrupt-controller@00a01000 {
    compatible = "arm,cortex-a7-gic";
};
```

- `intc` 是 label
- `interrupt-controller` 节点名
- `@00a01000` 寄存器物理基地址
- 使用：`&intc` 就可以引用此节点

**属性值的几种数据格式：**

1. **字符串**
   ```c
   compatible = "arm,cortex-a7";
   ```

2. **32 位无符号整数（尖括号 `<>` 包裹）**
   ```c
   reg = <0>;
   ```

3. **字符串列表，逗号隔开**
   ```c
   compatible = "fsl,imx6ull-gpmi-nand", "fsl,imx6ul-gpmi-nand";
   ```

### 43.3.3 常用标准属性

#### 1）compatible（兼容性属性，最重要）

格式：`"厂商,设备型号"`，可以写多个字符串。

**作用：** 完成设备树节点和 platform 驱动匹配。驱动里面 `of_match_table` 匹配 compatible 字符串，匹配成功，执行 probe 函数。

**dts：**
```c
compatible = "fsl,imx6ul-evk-wm8960", "fsl,imx-audio-wm8960";
```

**驱动代码：**
```c
static const struct of_device_id imx_wm8960_dt_ids[] = {
    { .compatible = "fsl,imx-audio-wm8960", },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, imx_wm8960_dt_ids);

static struct platform_driver imx_wm8960_driver = {
    .driver = {
        .name = "imx-wm8960",
        .of_match_table = imx_wm8960_dt_ids,
    },
    .probe  = imx_wm8960_probe,
    .remove = imx_wm8960_remove,
};
```

> **匹配规则**：从左向右依次对比 compatible 字符串，匹配到任意一个即绑定成功。

#### 2）model 属性

字符串，简单描述板子 / 设备信息。

```c
model = "wm8960-audio";
```

#### 3）status 属性

| 取值 | 含义 |
|------|------|
| `okay` | 设备可用，内核会解析此设备 |
| `disabled` | 设备禁用，内核忽略该节点 |
| `fail` | 设备出错，无法使用 |
| `fail-xxx` | 出错，附带错误信息 |

#### 4）`#address-cells`、`#size-cells`

写在父节点，规定子节点 `reg` 属性的解析规则：

- `#address-cells = <1>`：reg 中地址部分占用 1 个 32bit 单元
- `#size-cells = <1>`：reg 中长度部分占用 1 个 32bit 单元

**示例 1：**
```c
aips3: aips-bus@02200000 {
    #address-cells = <1>;
    #size-cells = <1>;
    dcp: dcp@02280000 {
        reg = <0x02280000 0x4000>;
    };
};
```

**示例 2（size-cells=0，没有长度）：**
```c
spi4 {
    #address-cells = <1>;
    #size-cells = <0>;
    gpio_spi: gpio_spi@0 {
        reg = <0>;
    };
};
```

#### 5）reg 属性

描述外设寄存器物理地址范围，格式 `reg = <基地址 长度>;`；可以写多组地址范围。

```c
uart1: serial@02020000 {
    reg = <0x02020000 0x4000>;
};
```

#### 6）ranges 属性（地址转换表）

格式：`ranges = <子总线地址 父总线地址 长度>;`

- `ranges;`（空）：子总线地址 = 父总线物理地址，不需要地址转换，I.MX6ULL soc 节点就是空 ranges
- 非空：做地址偏移转换

```c
soc {
    compatible = "simple-bus";
    #address-cells = <1>;
    #size-cells = <1>;
    ranges = <0x0 0xe0000000 0x00100000>;
    serial {
        reg = <0x4600 0x100>;
    };
};
```

`serial` 实际物理地址 = `0xe0000000 + 0x4600 = 0xe0004600`

> **废弃属性**：`name`、`device_type`，仅 cpu/memory 节点还会使用 `device_type`。

### 43.3.4 根节点的 compatible 属性，内核如何匹配板子

**设备树出现之前：machine id 机制**

U-Boot 传递 machine id（r1 寄存器）给内核；内核通过 `MACHINE_START` 宏定义 `machine_desc`，对比 machine id，确定支持哪块板子。

**使用设备树之后：DT_MACHINE_START**

不再使用 machine id。

1. dts 根节点 `/` 的 `compatible` 属性
2. 内核 `DT_MACHINE_START` 定义的 `machine_desc` 里面有 `.dt_compat` 兼容列表
3. 内核启动 `start_kernel()` → `setup_arch()` → `setup_machine_fdt()` → `of_flat_dt_match_machine()`
4. 将设备树根节点 compatible 和内核各个 `dt_compat` 表做字符串比对，找到匹配的 `machine_desc`；匹配失败，内核启动直接卡死

```c
// imx6ull-alientek-emmc.dts 根节点
/ {
    model = "Freescale i.MX6 ULL 14x14 EVK Board";
    compatible = "fsl,imx6ull-14x14-evk", "fsl,imx6ull";
};

// 内核 imx6ul_dt_compat[] = {"fsl,imx6ul", "fsl,imx6ull", NULL};
// 匹配上 "fsl,imx6ull"，内核正常启动
```

> 如果根节点 compatible 全部匹配失败，`Starting kernel…` 之后串口无任何输出。

### 43.3.5 追加或修改已有节点内容

`imx6ull.dtsi` 是 SOC 公共头文件，**严禁直接修改 dtsi！** 在板级 `.dts` 文件中，使用 `&label` 引用 dtsi 中已经定义好的节点，修改属性、增加子节点。

**示例，修改 i²C1 节点：**

`imx6ull.dtsi` 中定义：
```c
i2c1: i2c@021a0000 {
    #address-cells = <1>;
    #size-cells = <0>;
    compatible = "fsl,imx6ul-i2c", "fsl,imx21-i2c";
    reg = <0x021a0000 0x4000>;
    status = "disabled";
};
```

在 `imx6ull-alientek-emmc.dts` 板级 dts 里面，用 `&i2c1` 引用：
```c
&i2c1 {
    clock-frequency = <100000>;
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_i2c1>;
    status = "okay";    /* 修改属性：由 disabled 改为 okay */

    /* 新增子节点 fxls8471 */
    fxls8471@1e {
        compatible = "fsl,fxls8471";
        reg = <0x1e>;
    };
};
```

**效果：**

1. 修改原有属性：`status = "okay"`，新增 `clock-frequency` 等
2. 添加全新子节点 `fxls8471@1e`
3. 修改只作用于当前这块开发板，不会影响其他板子

## 43.4 创建小型模板设备树

实际产品开发不会从零完整写 dts，都是在 SOC 厂商提供 dts 基础上修改；本节做练习，手写一个精简版 `myfirst.dts`，熟悉设备树层级、节点、属性语法。

**需要在 dts 描述硬件：**

1. I.MX6ULL，Cortex-A7 单核 CPU
2. OCRAM：物理起始 `0x00900000`，大小 `0x20000`（128KB）
3. ecspi1（AIPS1 域）：`0x02008000`，大小 `0x4000`
4. usbotg1（AIPS2 域）：`0x02184000`，大小 `0x4000`
5. rngb（AIPS3 域）：`0x02284000`，大小 `0x4000`

```c
/ {
    compatible = "fsl,imx6ull-alientek-evk", "fsl,imx6ull";

    cpus {
        #address-cells = <1>;
        #size-cells = <0>;

        // CPU0 节点
        cpu0: cpu@0 {
            compatible = "arm,cortex-a7";
            device_type = "cpu";
            reg = <0>;
        };
    };

    // soc 节点，SOC 内部外设总父节点
    soc {
        #address-cells = <1>;
        #size-cells = <1>;
        compatible = "simple-bus";
        ranges;

        // ocram 内部 RAM
        ocram: sram@00900000 {
            compatible = "fsl,lpm-sram";
            reg = <0x00900000 0x20000>;
        };

        // AIPS1 域
        aips1: aips-bus@02000000 {
            compatible = "fsl,aips-bus", "simple-bus";
            #address-cells = <1>;
            #size-cells = <1>;
            reg = <0x02000000 0x100000>;
            ranges;

            // ecspi1 属于 aips1 子节点
            ecspi1: ecspi@02008000 {
                #address-cells = <1>;
                #size-cells = <0>;
                compatible = "fsl,imx6ul-ecspi", "fsl,imx51-ecspi";
                reg = <0x02008000 0x4000>;
                status = "disabled";
            };
        };

        // AIPS2 域
        aips2: aips-bus@02100000 {
            compatible = "fsl,aips-bus", "simple-bus";
            #address-cells = <1>;
            #size-cells = <1>;
            reg = <0x02100000 0x100000>;
            ranges;

            // usbotg1 属于 aips2 子节点
            usbotg1: usb@02184000 {
                compatible = "fsl,imx6ul-usb", "fsl,imx27-usb";
                reg = <0x02184000 0x4000>;
                status = "disabled";
            };
        };

        // AIPS3 域
        aips3: aips-bus@02200000 {
            compatible = "fsl,aips-bus", "simple-bus";
            #address-cells = <1>;
            #size-cells = <1>;
            reg = <0x02200000 0x100000>;
            ranges;

            // rngb 属于 aips3 子节点
            rngb: rngb@02284000 {
                compatible = "fsl,imx6sl-rng", "fsl,imx-rng", "imx-rng";
                reg = <0x02284000 0x4000>;
            };
        };
    };
};
```

### 层级结构梳理
根节点 /
├─ cpus
│   └─ cpu0: cpu@0          //单核Cortex-A7
└─ soc                      //SOC外设总父节点
    ├─ ocram: sram@00900000
    ├─ aips1: aips-bus@02000000
    │   └─ ecspi1: ecspi@02008000
    ├─ aips2: aips-bus@02100000
    │   └─ usbotg1: usb@02184000
    └─ aips3: aips-bus@02200000
        └─ rngb: rngb@02284000

### 关键点解析

1. **根节点 `/`**：必须存在，`compatible` 用于内核匹配 `machine_desc`
2. **cpus 父节点**：描述 CPU；`#size-cells = <0>`，cpu 的 reg 只写地址，无长度
3. **soc 节点**：SOC 所有外设控制器的总父节点
   - `compatible = "simple-bus"`
   - `ranges;` 空值：子节点地址直接等于父物理地址，不做地址偏移转换
   - `#address-cells = <1>`、`#size-cells = <1>`，子节点 reg 格式 `<基地址 长度>`
4. **aips1/aips2/aips3** 是 I.MX6ULL 内部总线域，作为 soc 的子节点；每个域下挂载对应外设控制器
5. **节点命名规则**：`label: 节点名@物理基地址 {}`；`reg=<物理基地址 长度>` 描述寄存器资源
6. **status = "disabled"**：设备默认关闭，需要使用时后续用 `&label` 修改为 `okay`

## 43.6 特殊节点

根节点 `/` 下面有两个特殊子节点：`aliases`、`chosen`。

### 43.6.1 aliases 子节点

```c
aliases {
    can0 = &flexcan1;
    can1 = &flexcan2;
    ethernet0 = &fec1;
    ethernet1 = &fec2;
    gpio0 = &gpio1;
    gpio1 = &gpio2;
    ......
    spi0 = &ecspi1;
    spi1 = &ecspi2;
    spi2 = &ecspi3;
    spi3 = &ecspi4;
    usbphy0 = &usbphy1;
    usbphy1 = &usbphy2;
};
```

- **aliases 含义**：别名，作用是给设备节点起简短别名，方便内核或者设备树引用节点
- **语法**：`别名 = &label;`，`&label` 就是设备节点的标签
- 举例：`spi0 = &ecspi1;`，`ecspi1` 是硬件实际节点，别名叫做 `spi0`

> 补充：现在 DTS 开发更常用直接加 label，用 `&label` 引用，aliases 别名更多是给内核驱动识别设备编号用。

**一句话：aliases 就是给设备起短名字。**

### 43.6.2 chosen 子节点

`chosen` 不是真实硬件设备，它的核心用途：**U-Boot 向 Linux 内核传递启动参数**，最关键参数就是 `bootargs`。

**dts 源码里的 chosen（imx6ull-alientek-emmc.dts）：**

```c
chosen {
    stdout-path = &uart1;
};
```

`stdout-path = &uart1;`：标准输出串口选择 uart1，开发板串口控制台。

但是当我们进入到 `/proc/device-tree/chosen` 目录里面，会发现多了 `bootargs` 这个属性：

![图5-4 chosen节点目录](photo/设备树实验/5-4%20chosen节点目录.png)

输入 `cat` 命令查看 `bootargs` 这个文件内容：

![图5-5 bootargs文件内容](photo/设备树实验/5-5%20bootargs文件内容.png)

这个字符串，就是 U-Boot 环境变量 `bootargs` 的值。

**bootargs 是谁加上去的？**

是 U-Boot 在启动内核前，动态修改内存中的 dtb 二进制，给 chosen 节点追加 bootargs 属性。

U-Boot 源码文件：`common/fdt_support.c`，函数 `fdt_chosen()`：

```c
int fdt_chosen(void *fdt)
{
    int nodeoffset;
    int err;
    char *str;

    err = fdt_check_header(fdt);
    if (err < 0) {
        printf("fdtchosen:");
        return err;
    }

    /* 查找 chosen 节点，找不到就新建 */
    nodeoffset = fdt_find_or_add_subnode(fdt, 0, "chosen");
    if (nodeoffset < 0)
        return nodeoffset;

    /* 读取 U-Boot 环境变量 bootargs */
    str = getenv("bootargs");
    if (str) {
        /* 往 dtb 的 chosen 节点添加 bootargs 属性 */
        err = fdt_setprop(fdt, nodeoffset, "bootargs", str, strlen(str) + 1);
        if (err < 0) {
            printf("WARNING: could not set bootargs %s.\n", fdt_strerror(err));
            return err;
        }
    }
    return fdt_fixup_stdout(fdt, nodeoffset);
}
```

**代码逐行解析：**

- `fdt_find_or_add_subnode`：在内存里的 dtb 中查找 chosen 节点，如果不存在，自动创建
- `getenv("bootargs")`：读取 U-Boot 的 bootargs 环境变量
- `fdt_setprop`：动态写入 dtb，增加 bootargs 属性，值等于环境变量 bootargs
- `fdt_fixup_stdout`：处理 stdout-path 标准输出串口

**完整调用链路：**

框起来的部分就是函数 `do_bootm_linux` 函数的执行流程，也就是说 `do_bootm_linux` 函数会通过一系列复杂的调用，最终通过 `fdt_chosen` 函数在 chosen 节点中加入了 bootargs 属性。而我们通过 `bootz` 命令启动 Linux 内核的时候会运行 `do_bootm_linux` 函数，至此，可知道一切事情的源头都源于如下命令：

```bash
bootz 80800000 – 83000000
```

当我们输入上述命令并执行以后，`do_bootz` 函数就会执行，然后一切就按照下图的流程运行：
![图5-7 fdt_chosen系统调用](photo/设备树实验/5-7%20fdt_chosen系统调用.png)

**图中含义解释：**

| 函数 | 说明 |
|------|------|
| `bootz` | U-Boot 命令，用来启动 zImage 内核，`bootz 80800000 – 83000000` |
| `do_bootz()` | bootz 命令对应的处理函数 |
| `do_bootm_states()` | bootm 系列状态机函数 |
| `boot_selected_os()` | 选定要启动的操作系统，把函数指针 `boot_fn` 赋值为 `do_bootm_linux` |
| `boot_fn()` | 调用函数指针，实际运行 `do_bootm_linux()` |
| `boot_prep_linux()` | Linux 启动前预处理，核心就是处理设备树的修改（添加 bootargs） |
| `image_setup_linux()` | Linux 镜像相关设置 |
| `image_setup_libfdt()` | libfdt 设备树库相关配置 |
| `fdt_chosen()` | 最终函数！在内存里的 dtb 的 chosen 节点，新增 bootargs 属性，值取自 U-Boot 环境变量 bootargs |

> **总结**：执行 `bootz` → 层层进入 `do_bootm_linux`，在 `boot_prep_linux` 预处理阶段，通过 `image_setup` 系列函数，调用 `fdt_chosen` 修改内存 DTB，填入 bootargs。

## 43.7 Linux 内核解析 DTB 文件

Linux 内核在启动的时候会解析 DTB 文件，然后在 `/proc/device-tree` 目录下生成相应的设备树节点文件。

![图5-8 内核解析dtb](photo/设备树实验/5-8%20内核解析dtb.png)

**流程说明：**

1. `start_kernel()`：Linux 内核启动入口总函数，内核启动的起点
2. `setup_arch()`：体系架构相关初始化函数，在这里开始设备树解析工作
3. `unflatten_device_tree()`：设备树解析入口函数
4. `__unflatten_device_tree()`：内部函数，准备解析工作
5. `unflatten_dt_node()`：核心解析函数，递归遍历 DTB 二进制，解析每一个节点、属性，在内核内存中构建 `device_node` 节点树

**解析完成两件事：**

① 内核内存中构建完整设备树结构体链表（驱动用 OF 函数读取）

② 内核自动创建虚拟文件系统 `/proc/device-tree`，供用户态调试查看

**名词解释：**

- **DTB**：设备树的二进制文件，U-Boot 加载到内存，传递给内核
- **unflatten**：直译"展开"，把扁平二进制 DTB，展开成内核中树形的 `device_node` 结构体

## 43.8 绑定信息文档

### 1）绑定文档是什么？

设备树绑定文档（bindings），是内核源码里的说明文档：

![图5-9 绑定文档](photo/设备树实验/5-9%20绑定文档.png)

规定某一类硬件在设备树节点里**必须写哪些属性**、**可选哪些属性**、**属性格式是什么**、**compatible 字符串怎么写**。写 dts 添加硬件节点前，优先看对应的绑定文档，不能自己随便乱写属性。

### 2）存放路径

内核源码路径：`Linux源码目录/Documentation/devicetree/bindings`

bindings 文件夹下按硬件类别分文件夹存放文档：`arm`、`i2c`、`spi`、`clock`、`ata`、`bus`……

### 3）举例：i.MX I²C 绑定文档

文件：`Documentation/devicetree/bindings/i2c/i2c-imx.txt`

文档分成三大部分：

**Required properties（必填属性）**：写节点必须有的属性，少一个就会匹配失败

| 属性 | 说明 |
|------|------|
| `compatible` | 兼容性字符串，用来和驱动匹配（例如 `fsl,imx51-i2c`） |
| `reg` | 外设寄存器物理基地址 + 寄存器长度 |
| `interrupts` | 中断信息 |
| `clocks` | 时钟信息 |

**Optional properties（可选属性）**：可加可不加

| 属性 | 说明 |
|------|------|
| `clock-frequency` | I²C 总线频率；不写默认 100kHz |
| `dmas`、`dma-names` | DMA 相关配置 |

**Examples（示例节点代码）**：直接给完整 dts 节点模板，可以参考复制修改

## 43.9 设备树常用 OF 操作函数

**OF 函数**：内核提供读取设备树节点 / 属性的 API，前缀统一 `of_`，头文件 `include/linux/of.h`。

> **核心思想**：驱动代码想要拿到 DTS 里写的硬件信息（reg、compatible 等），先拿到 `device_node` 节点，再读取节点里的属性。

### 43.9.1 查找节点的 OF 函数

`struct device_node`：内核用来描述设备树一个节点的结构体。

```c
struct device_node {
    const char *name;              /* 节点名字 */
    const char *type;              /* 设备类型 */
    phandle phandle;
    const char *full_name;         /* 节点全名 */
    struct fwnode_handle fwnode;
    struct property *properties;   /* 属性链表 */
    struct device_node *parent;    /* 父节点 */
    struct device_node *child;     /* 子节点 */
    struct device_node *sibling;   /* 兄弟节点 */
    struct kobject kobj;
    unsigned long _flags;
    void *data;
};
```

| 函数 | 功能 |
|------|------|
| `of_find_node_by_name(from, name)` | 通过节点 name 名字查找节点；`from=NULL` 从根节点开始查找 |
| `of_find_node_by_type(from, type)` | 通过 `device_type` 属性查找节点 |
| `of_find_compatible_node(from, type, compatible)` | 通过 `device_type` + compatible 字符串查找节点；type 传 NULL 代表忽略 type |
| `of_find_matching_node_and_match(from, matches, match)` | 根据 `of_device_id` 匹配表查找节点，platform 驱动常用 |
| `of_find_node_by_path(path)` | 通过节点全路径查找节点，例 `/backlight` |

### 43.9.2 查找父/子节点 OF 函数

| 函数 | 功能 |
|------|------|
| `of_get_parent(node)` | 获取指定节点的父节点 |
| `of_get_next_child(node, prev)` | 迭代遍历子节点；`prev=NULL` 从第一个子节点开始，循环获取下一个子节点 |

### 43.9.3 提取属性值 OF 函数

`struct property` 结构体，用来描述节点的一条属性：

```c
struct property {
    char *name;            /* 属性名字 */
    int length;            /* 属性值长度 */
    void *value;           /* 属性数据 */
    struct property *next; /* 指向下一条属性 */
    unsigned long _flags;
    unsigned int unique_id;
    struct bin_attribute attr;
};
```

| 函数 | 功能 |
|------|------|
| `of_find_property(np, name, lenp)` | 查找指定名字的属性，返回 property 指针，lenp 带出属性字节长度 |
| `of_property_count_elems_of_size(np, propname, elem_size)` | 统计属性数组里面元素个数 |
| `of_property_read_u32_index(np, propname, index, out_value)` | 读取数组属性里面指定下标的 u32 数值（reg 数组常用） |
| `of_property_read_u8/u16/u32/u64_array()` | 读取属性整个数组，批量读出多个数值，reg 属性最常用 |
| `of_property_read_u8/u16/u32/u64()` | 属性只有单个整数时使用，直接读一个数字 |
| `of_property_read_string(np, propname, out_string)` | 读取字符串类型属性，例如 compatible |
| `of_n_addr_cells(np)` | 读取 `#address-cells` 属性 |
| `of_n_size_cells(np)` | 读取 `#size-cells` 属性 |

> 返回值：0 成功；负数代表错误码，`-EINVAL` 属性不存在，`-ENODATA` 无数据，`-EOVERFLOW` 数组长度不足。

### 43.9.4 其他常用 OF 函数

**1. `of_device_is_compatible(device, compat)`**

判断节点 compatible 属性是否包含指定字符串，校验兼容性。

**2. `of_get_address(dev, index, size, flags)`**

读取 `reg/assigned-address` 地址属性，拿到原始地址。

**3. `of_translate_address(dev, in_addr)`**

把设备树读取的地址转换成物理地址。

**4. `of_address_to_resource(dev, index, r)`**

把 `reg` 属性转换成内核 `struct resource` 资源结构体：

```c
struct resource {
    resource_size_t start;   // 起始物理地址
    resource_size_t end;     // 结束物理地址
    const char *name;
    unsigned long flags;     // 资源标记 IORESOURCE_MEM / IORESOURCE_IRQ
    struct resource *parent, *sibling, *child;
};
```

常见 flags：

| flags | 含义 |
|-------|------|
| `IORESOURCE_MEM` | 内存资源（寄存器） |
| `IORESOURCE_IRQ` | 中断资源 |
| `IORESOURCE_REG` | 寄存器资源 |

**5. `of_iomap(np, index)`**

设备树版本推荐使用，替代 `ioremap` 功能：读取 `reg` 属性里面的物理地址，直接完成物理→虚拟地址映射，返回虚拟地址 `void __iomem *`。

- `index`：reg 有多段地址时指定段号，单段 reg 填 0
- 返回 `NULL` 代表映射失败
